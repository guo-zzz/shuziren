## 0. 结论摘要（先看这五条）

1. **本模块不参与初赛评分。** 初赛是平台自动运行我们的 Docker 镜像、对对话模型的输出做离线测评，数字人形象和前端界面一分都不占。本模块的价值集中在 **12 月下旬的总决赛答辩与作品展示**。所以本模块的原则是：**够用、稳定、别烧算力**。
2. **推荐路线：Live2D / 2.5D 形象 + 流式 TTS + WebRTC 推流**，底座直接复用开源框架，不自研渲染与口型算法。三条候选底座见第 3 节：`LiveTalking`、`Open-LLM-VTuber`、`OpenTalking`。
3. **真正能做出差异的不是"数字人"本身，而是"情感联动"**：把对话模型输出的情绪标签同时驱动 TTS 的情感参数和数字人的表情/动作，让"共情"被看得见。这是本项目相对通用数字人方案的创新点，也是答辩现场最容易打动评委的 30 秒。
4. **延迟基准**：首包 3 秒以内算合格，1.5 秒以内算优秀。同行项目的实测锚点是级联方案 8G 显存 / 首包约 3 秒（VideoChat，单张 A100 实测）。
5. **尽量不要把数字人塞进初赛提交的 Docker 镜像。** 初赛镜像跑的是算法推理，多挂一个 WebRTC + TTS 服务只会增加跑挂的概率。建议数字人 Demo 独立成一个服务/仓库，决赛前再决定是否合并。

## 1. 本模块的定位与边界

### 1.1 我负责什么

### 1.2 一个必须提前对齐的判断：数字人不进初赛镜像

赛事要求初赛作品是 Docker 镜像，入口 `/participant/run_all.sh`，平台在离线环境自动读取测试数据、运行推理、按格式输出预测结果，全程无人干预（详见赛事介绍第 13、14 页）。这条约束推到本模块有两个结论：

- 初赛阶段，"数字人做得好不好"对排名**零影响**；
- 如果把数字人服务塞进初赛镜像，一旦它启动失败或超时，整个镜像判运行失败，赔上全队的提交机会。

**建议**：数字人 Demo 独立成一个仓库/服务，初赛镜像只保留对话模型推理。这条建议需要在和钟老师讨论时明确，因为它会影响邹艾融的整合方式。

## 2. 数字人形象：三条技术路线

### 2.1 路线对比

| 维度 | A. 2D 卡通 / Live2D | B. 2D 真人视频驱动（Talking Head） | C. 3D 模型 |
| --- | --- | --- | --- |
| 代表方案 | Open-LLM-VTuber、live2d-py | Wav2Lip、MuseTalk、LatentSync、EchoMimicV2 | TalkingHead.js、Unity + uLipSync、NVIDIA Audio2Face |
| 口型实现 | 音频转表情参数（口型开合 + 眨眼） | 音频直接重绘嘴部像素 | 音频转 viseme / blendshape |
| 显存占用 | 几乎为零 | 需要 GPU 常驻，数 GB 起 | 服务端零显存（浏览器渲染） |
| 观感 | 二次元、亲和、稳定不掉帧 | 最真实，但容易出现嘴部糊、抖动 | 中等，风格化 |
| 制作成本 | 低，换模型文件即可 | 高，需要形象素材与调参 | 中，需要模型与绑定 |
| 和"情感陪伴"赛题的契合度 | **高**，虚拟陪伴形象是成熟产品形态 | 中，真人形象偏"客服/主播" | 中 |
| 现场演示风险 | 低 | 中高（显存、掉帧） | 低 |

### 2.2 选型建议

**首选 A（2D/Live2D）+ 备选 B（2D 真人）**，理由：

- 赛题关键词是"数字人情感陪伴与智能对话"，陪伴型产品的主流形态就是二次元形象，用户接受度高，评委也不会觉得违和；
- 2D 路线把 GPU 全部留给对话模型和 TTS，这对我们只有 2 卡 4090 的开发实例非常关键；
- 决赛现场演示最怕翻车，2D 路线的稳定性显著优于视频驱动；
- 如果时间允许，在决赛版 Demo 里再叠加一路"真人形象"作为对比展示，说明方案可扩展。

**C 路线作为技术备选**保留：纯浏览器渲染的 TalkingHead.js 不需要服务端 GPU，如果现场只能用一台笔记本演示，这是唯一稳妥的方案。

## 3. 可直接复用的开源底座（本模块重点）

调研的基本判断：**这个领域已经有成熟到"开箱即用"的整套框架，我们没有理由自己拼装 ASR + LLM + TTS + 口型 + 推流**。下面是按用途分类的候选，星标数为 2026-09-25 抓取。

### 3.1 实时对话数字人引擎（最贴合我们需求）

| 项目 | 星标 | 许可证 | 最近更新 | 能力 | 备注 |
| --- | --- | --- | --- | --- | --- |
| [lipku/LiveTalking](https://github.com/lipku/LiveTalking) | 9.6k | Apache-2.0 | 2026-09-13 | 实时交互流式数字人引擎；支持 ernerf / musetalk / wav2lip / Ultralight 四种模型；支持**说话被打断**；WebRTC / RTMP / 虚拟摄像头输出；支持声音克隆、动作编排、多并发 | 中文文档 + Gitee 镜像；实测环境 Ubuntu 22.04 + Python 3.12 + PyTorch 2.9.1 + CUDA 12.8；自带 `index.html` / `avatar.html` / `admin.html` 三个页面；需开放 TCP:8010 与 UDP:1-65536 |

**这条最值得优先验证。** 它把我们最头疼的"实时音视频推流 + 口型 + 打断"全部打包好了，还自带前端页面和形象生成页，我们的工作会变成"接对话模型 + 换形象 + 调延迟"。

### 3.2 陪伴型虚拟人（情感场景最贴题）

### 3.6 参考基线：延迟与显存

[Henry-23/VideoChat](https://github.com/Henry-23/VideoChat)（1.3k 星）给出了公开的实测数字，是我们做延迟预算的锚点：

| 方案 | 显存 | 首包延迟 |
| --- | --- | --- |
| 级联（ASR → LLM → TTS → 口型） | 约 8G | 约 3 秒（单张 A100） |
| 端到端语音（MLLM → 口型） | 约 20G | 约 7 秒（单张 A100） |

它的技术选型是 FunASR + Qwen + GLM-4-Voice + GPT-SoVITS/CosyVoice/edge-tts + MuseTalk，和我们规划的组合高度一致，可以直接对照它的工程量评估我们自己的工作量。

**结论：级联方案 8G 显存，我们单张 4090（24G）绰绰有余；端到端方案 20G 且首包 7 秒，体验明显更差，不建议作为主方案。**

## 4. 语音链路

### 4.1 语音识别（ASR）

| 方案 | 星标 | 许可证 | 推荐理由 |
| --- | --- | --- | --- |
| [modelscope/FunASR](https://github.com/modelscope/FunASR) | 20.5k | MIT | **首选**。阿里出品，中文识别强，支持流式识别，今日仍有提交，国内下载顺畅 |
| [m-bain/whisperX](https://github.com/m-bain/whisperX) | 24.2k | - | 备选，词级时间戳与说话人分离做得好，但中文流式场景不如 FunASR |
| [QwenLM/Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR) | 3.6k | - | 新方案，可作为对比实验 |

### 4.2 语音合成（TTS）——本模块最关键的选择

赛题要求"共情表达"，所以 TTS 的核心指标不是"像不像人"，而是**能不能带着情绪说话**。

| 方案 | 星标 | 许可证 | 情感能力 | 其他关键能力 |
| --- | --- | --- | --- | --- |
| [index-tts/index-tts](https://github.com/index-tts/index-tts) | 24.2k | 以仓库为准 | **强**。IndexTTS-2.5 支持细粒度情感控制、音色与情感解耦 | 零样本音色克隆、时长控制（0.5x–2.0x）、拼音/CMU 音素纠音、支持 vLLM 部署 |
| [QwenAudio/CosyVoice](https://github.com/QwenAudio/CosyVoice) | 23.8k | Apache-2.0 | **强**。支持 instruct 指令控制情感、语速、音量 | Fun-CosyVoice 3.0 **双向流式，延迟低至 150ms**；9 种语言 + 18 种中文方言；支持音色克隆 |
| [OpenBMB/VoxCPM](https://github.com/OpenBMB/VoxCPM) | 38.0k | 以仓库为准 | 中高。可通过自然语言描述"设计"音色与情感 | 2B 参数、30 语言、48kHz 输出，音质最好但推理开销最大 |
| [RVC-Boss/GPT-SoVITS](https://github.com/RVC-Boss/GPT-SoVITS) | 62.1k | MIT | 中。情感主要靠参考音频带出 | 1 分钟数据即可克隆音色，社区最成熟 |
| [2noise/ChatTTS](https://github.com/2noise/ChatTTS) | 39.9k | **AGPL-3.0** | 中。面向日常对话的口语化 | 对话语气自然，但许可是 AGPL，商用需注意 |
| [fishaudio/fish-speech](https://github.com/fishaudio/fish-speech) | 32.8k | 以仓库为准 | 中 | SOTA 开源 TTS，被 Duix.Avatar 采用 |
| [rany2/edge-tts](https://github.com/rany2/edge-tts) | 12.0k | - | 弱 | **零成本、零显存、秒级可用**，作为演示兜底 |

**建议**：主力 **IndexTTS-2.5**（情感可控最直接对应赛题）或 **Fun-CosyVoice 3.0**（150ms 流式延迟对体感帮助最大），兜底 **edge-tts**。

两个 TTS 一起准备是有必要的：演示当天任何一路出问题，另一路能顶上。

### 4.3 断句与打断（VAD）

- **VAD（语音活动检测）**：用于判断用户是否在说话、何时说完。推荐 Silero VAD 或 FunASR 自带的端点检测能力。
- **打断（barge-in）**：用户开口时立即停止 TTS 播放、清空待播队列、丢弃当前未完成回复。**这是"陪伴感"和"客服感"的分水岭**，评委很容易感知到。LiveTalking、Open-LLM-VTuber、opentalking 都原生支持，这也是选它们的重要原因。

## 5. 口型同步方案

### 5.1 三条技术路线

| 路线 | 原理 | 代表项目 | 适用形象 |
| --- | --- | --- | --- |
| 参数/音素驱动 | 音频 → 音素或 viseme → 驱动嘴部参数 | TalkingHead.js（1.6k）、live2d-py（573）、Rhubarb Lip Sync（2.6k）、Unity uLipSync（1.7k） | Live2D、3D 模型 |
| 视频重绘驱动 | 音频 → 逐帧重绘嘴部区域 | Wav2Lip（13.2k）、MuseTalk（6.6k）、LatentSync（6.1k）、EchoMimicV2（4.7k）、LivePortrait（19.1k） | 真人视频形象 |
| 3D 表情驱动 | 音频 → blendshape / 表情系数 | NVIDIA Audio2Face、ARKit blendshape 体系 | 3D 模型 |

### 5.2 对比与建议

| 维度 | 参数驱动 | 视频重绘 | 3D 表情 |
| --- | --- | --- | --- |
| 显存 | 几乎为零 | 数 GB 常驻 | 服务端零 |
| 延迟 | 极低（毫秒级） | 中高（需逐帧生成） | 低 |
| 真实感 | 低 | 高 | 中 |
| 稳定性 | 高 | 中（易抖动、糊嘴） | 高 |
| 与 Live2D 路线配合 | 完美 | 不适用 | 不适用 |

**建议**：既然形象选 2D/Live2D 路线，口型就用**参数驱动**，把 GPU 省给对话模型与 TTS。如果决赛要展示真人形象，用 **MuseTalk**（被 VideoChat、Linly-Talker 同时选用，是当前实时唇形同步的事实标准之一）。

## 6. 与后端对话模型的联动架构（本模块核心）

### 6.1 数据流

```
[麦克风] → VAD 静音检测 → ASR 识别 → ─┐
                                      ↓
                            [对话模型服务（张力文）]
                                      ↓  流式文本 + 情绪标签
                                 [分句器]
                                      ↓
                          [TTS 流式合成] → 音频块
                                      ↓
                    [口型驱动（参数/视频）] → 视频帧
                                      ↓
                          [WebRTC / RTMP 推流]
                                      ↓
                              [浏览器播放] → 字幕同步
```

### 6.2 协议选型

| 用途 | 建议协议 | 说明 |
| --- | --- | --- |
| 音视频推流 | **WebRTC** | 低延迟，LiveTalking / opentalking / Linly-Talker-Stream 均采用；LiveTalking 需要开放 TCP:8010 与 UDP 1-65536 |
| 对话模型调用 | **HTTP + SSE 流式**（或 OpenAI 兼容 `/v1/chat/completions`） | 与张力文约定的统一接口，便于他们换模型时我这侧不改代码 |
| 控制信令 / 字幕事件 | **WebSocket** | 打断指令、会话状态、字幕逐字推送 |

### 6.3 三个必须做对的设计

1. **流式分句**：不要等大模型把整段说完才送去 TTS。一遇到标点（。！？）就切句送合成，首包延迟能从 3 秒压到 1.5 秒以内。
2. **打断优先**：用户一开口，立刻停播、清队列。实现上让 VAD 事件优先于 TTS 播发队列。
3. **情感联动（创新点）**：对话模型除了返回文本，还要返回情绪标签；这个标签同时驱动
   - TTS：情感风格、语速、音量（CosyVoice 的 instruct、IndexTTS 的情感控制都支持）；
   - 数字人：表情与动作（LiveTalking 的动作编排、Live2D 的表情参数）。

   效果就是：用户倾诉低落，数字人**语气变温柔、表情收敛**；用户说到开心的事，**语气轻快、表情明亮**。这一步是我们和"套壳数字人"的分界线。

### 6.4 延迟预算（目标：首包 ≤ 1.5 秒）

| 环节 | 目标耗时 | 备注 |
| --- | --- | --- |
| VAD 判定用户说完 | 0.1 s | 端点检测阈值可调，设太紧会抢话 |
| ASR 识别 | 0.3 s | 流式识别，边说边出字 |
| 对话模型首 token | 0.3 – 1.0 s | 取决于模型规模，小模型优先 |
| 首句分句 + TTS 首包 | 0.15 – 0.5 s | CosyVoice 双向流式可低至 150ms |
| 口型生成 + 推流 | 0.2 – 0.5 s | 参数驱动远快于视频重绘 |
| 网络往返 | 0.1 s | 本地演示可忽略 |
| **合计** | **约 1.15 – 2.5 s** | 控制在 3 秒内即达到同行水平 |

### 6.5 部署注意事项（踩坑预防）

- **麦克风需要安全上下文**：浏览器只在 https 或 localhost 下允许访问麦克风。远程访问必须配 https 反向代理（Open-LLM-VTuber 文档明确提示）。
- **端口与防火墙**：WebRTC 需要放通 UDP 大范围端口，校园网/云服务器安全组要提前配置。
- **模型下载走国内源**：模型权重优先从 ModelScope 获取，HuggingFace 直连大概率失败。
- **显存分配**：级联方案 8G 左右即可（参考 VideoChat 实测），我们单张 4090 有充足余量；但不要把对话模型和 TTS 都塞进同一张卡还开多路并发。
- **许可证**：Fay 是 GPL-3.0、ChatTTS 是 AGPL-3.0，若项目后续有商用规划，选型时要避开或单独评估。

## 7. 情绪标签体系（建议团队统一，需要唐应杰与张力文确认）

这是对话模型（张力文）→ TTS 情感参数 + 数字人表情（我）之间的公共接口，**必须三方统一，否则我这边的情感联动无法实现**。

草案（6 类，够用且易于标注）：

| 标签 | 典型场景 | TTS 情感映射 | 数字人表现 |
| --- | --- | --- | --- |
| 开心 | 分享好消息、被认可 | 轻快、语速略快、音调上扬 | 微笑、点头 |
| 平静 | 日常闲聊 | 自然、中速 | 平稳、偶尔眨眼 |
| 低落 | 情绪倾诉、受挫 | 温柔、语速放慢、音量略降 | 表情收敛、倾听姿态 |
| 焦虑 | 考试、就业压力 | 沉稳、语速放缓、语气笃定 | 前倾、安抚性点头 |
| 愤怒 | 抱怨、人际冲突 | 平静克制、语速平缓 | 中性表情、避免过度反应 |
| 惊喜 | 意外之喜 | 明亮、适度上扬 | 睁大眼睛、轻微后仰 |

注意两点：

- 标签数量不宜过多，否则 TTS 情感参数难以区分、数据标注成本也会失控；
- 如果唐应杰的评估口径里包含"回复情感恰当性"，这套标签可以直接作为评估的对齐依据。

## 8. Demo 构想

### 8.1 场景设定

**定位**：面向高校学生的情绪陪伴数字人。用户是压力大的大学生，数字人是可信赖的同龄伙伴。

三个可演示的痛点场景（与内容赛道的思政主题也能呼应）：
1. 学业受挫：挂科、论文写不下去
2. 就业焦虑：秋招失利、面试紧张
3. 宿舍人际：和室友闹矛盾

### 8.2 三档方案（按投入递增）

| 档位 | 组成 | 工作量 | 适用 |
| --- | --- | --- | --- |
| **稳妥版（建议先做）** | Open-LLM-VTuber 或 LiveTalking + Live2D 形象 + CosyVoice/IndexTTS + 对话模型服务 | 1 – 2 周 | 保证有可演示的成品 |
| **进阶版** | opentalking/LiveTalking + 真人 2D 形象（MuseTalk）+ 情感联动 + 打断 | 3 – 4 周 | 决赛主推 |
| **理想版** | 端到端语音对话（GLM-4-Voice / Qwen-Omni 类）+ 数字人 | 显存 20G、首包 7 秒 | 仅作为技术展望，不建议作为主方案 |

### 8.3 三分钟演示脚本（决赛用）

| 时间 | 演示内容 | 要展示的技术点 |
| --- | --- | --- |
| 0:00 – 0:40 | 用户语音提问："我这次考试又没过，感觉特别糟糕" | 完整语音链路：VAD → ASR → 对话模型的共情回应 |
| 0:40 – 1:20 | 数字人温柔回应，语速放慢、表情收敛 | **情感联动**：情绪标签驱动 TTS 与表情 |
| 1:20 – 1:50 | 用户打断："等一下，我先说个别的事" | **打断能力**：数字人立即停口倾听 |
| 1:50 – 2:30 | 用户提到上次聊过的话题，数字人主动承接 | **记忆融合**：与对话模型模块的联合成果 |
| 2:30 – 3:00 | 系统界面展示情绪曲线 / 会话记录 | 用可视化证明"共情"不是主观感受 |

演示脚本要和张力文、唐应杰对齐：第 4、5 分钟用到的记忆与情绪能力是他们的模块产出，**必须提前约定好接口和演示用例**，不能到现场才拼接。

### 8.4 降级预案

| 风险 | 降级方案 |
| --- | --- |
| 现场网络差 / 云端服务不可用 | 全部本地部署 + 提前录屏兜底 |
| GPU 不可用 | 切纯前端 TalkingHead.js 方案，或直接用预渲染视频演示 |
| TTS 合成太慢或卡顿 | 切 edge-tts（零显存，秒级） |
| 麦克风权限被浏览器拦截 | 改手动输入文字驱动，功能展示不受影响 |
| 数字人推流掉帧 | 降低输出分辨率与帧率，优先保口型和声音同步 |

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 本模块对初赛排名零贡献，却消耗时间 | 高 | 国庆前只做调研与选型，动手放到初赛提交之后 |
| 数字人服务影响初赛镜像稳定性 | 高 | 数字人独立成服务，初赛镜像不集成 |
| 4090 算力被演示环境占用 | 中 | 训练与演示分时使用；演示优先用参数驱动、轻量 TTS |
| 情感标签三方不统一 | 中 | 第 7 节草案尽早拉三方过一遍 |
| 开源项目停止维护或许可证冲突 | 中 | 主方案避开 AGPL/GPL 项目；锁定版本号，不追最新 main |
| 现场演示翻车 | 高 | 8.4 的三档降级预案 + 提前录屏 |
